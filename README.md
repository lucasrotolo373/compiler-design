# Compiler for a Custom Language — Java Implementation

> Full compiler pipeline: manual lexer, YACC/J parser with error recovery, semantic analysis with name mangling, RPN intermediate representation, and x86-32 assembly code generation.

## Overview

This project implements a complete compiler in Java for a custom language defined by the course specification at UNICEN. The compiler covers all classical stages of translation: lexical analysis, syntactic analysis, semantic analysis, intermediate code generation, and final code generation targeting x86-32 assembly (MASM32).

The parser acts as the main module (monolithic architecture) and drives the entire compilation process, invoking the lexer on demand and coordinating semantic actions at each grammar rule reduction.

## Language Features

The source language supports a mix of features from several paradigms:

- **Types:** unsigned 16-bit integers (`UI` suffix), 64-bit floating point (`D` exponent notation), multiline strings (delimited by `&`)
- **Control flow:** `if/else`, `do/while`, nested blocks with `{}`
- **Functions:** multiple return values (`float, int F(int X)`), lambda parameters
- **Variables:** type inference via assignment, variable reservation with `var`
- **Assignments:** multiple assignment (`a, b = f()`) with element count validation
- **I/O:** `print` statement

## Compiler Architecture

```
Source code
    │
    ▼
┌─────────────────────┐
│   Lexical Analyzer  │  Manual DFA implementation with transition matrix
│   AnalizadorLexico  │  Handles tokens, symbol table insertion, error recovery
└─────────────────────┘
    │  token stream
    ▼
┌─────────────────────┐
│   Parser (YACC/J)   │  LALR(1) parser generated from gramatica.y
│   gramatica.y       │  Full grammar + error recovery productions
│   Parser.java       │  Drives semantic actions at each reduction
└─────────────────────┘
    │  decorated parse tree
    ▼
┌─────────────────────┐
│  Semantic Analysis  │  Embedded in grammar actions
│  AccionesSemanticas │  Name mangling, scope management, type checking
│  AS1.java–AS15.java │  Multiple return validation, backpatching
└─────────────────────┘
    │  intermediate representation (RPN)
    ▼
┌─────────────────────┐
│   Code Generator    │  RPN → x86-32 assembly via auxiliary variable technique
│   GeneradorASM.java │  Targets MASM32
└─────────────────────┘
    │
    ▼
  output.asm (MASM32)
```

## Key Design Decisions

**Manual lexer with DFA transition matrix:** The lexer was implemented from scratch using a finite automaton encoded as a state transition matrix. This handles all token types including multiline strings, floating point with optional exponent, and unsigned integer suffixes.

**YACC/J parser as main module:** The parser is the entry point of the compiler. It calls the lexer when it needs the next token, rather than the lexer driving the parser. This is the standard architecture when using YACC-family tools.

**Name mangling for scope resolution:** Identifiers are stored in the symbol table with their full scope path as key (e.g., `X:MAIN:F` for variable `X` inside function `F` inside `MAIN`). This allows unambiguous resolution of identifiers in nested scopes without a separate scope stack per symbol.

**Backpatching for control flow:** Branch targets in the RPN intermediate representation are initially left empty and filled in retroactively once the target position is known. A jump stack tracks unresolved branches. This is standard practice for single-pass intermediate code generation.

**RPN intermediate representation:** All executable statements are translated to Reverse Polish Notation before code generation. RPN linearizes the expression tree, preserves operator precedence, and simplifies the final translation to assembly since operands are always processed before their operators.

**Auxiliary variable technique for x86-32 code generation:** The code generator translates RPN to x86-32 assembly using auxiliary (temporary) variables to hold intermediate results. This avoids complex register allocation while producing correct code.

## Symbol Table

Implemented as a `HashMap<String, TDSObject>` where the key is `lexeme:scope` (name-mangled identifier). Each entry stores:

- Type (`dfloat`, `uint`, `string`)
- Usage (`variable`, `constant`, `function`, `lambda`)
- Parameter passing mode
- List of return types (for multi-return functions)
- List of parameter types

## How to Build

1. Generate the parser from the grammar:
```bash
byaccj -Jclass=Parser gramatica.y
```

2. Compile the Java sources:
```bash
javac -cp . src/**/*.java
```

3. Run the compiler on a source file:
```bash
java AnalizadorSintactico.AnalizadorSintactico input.src
```

4. Assemble the output with MASM32:
```bash
ml /c /coff output.asm
link /subsystem:console output.obj
```
